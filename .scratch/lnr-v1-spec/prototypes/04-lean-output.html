1. What are the three tiers, and what does --json promise?

      
Lean default / --verbose / --json. Flip the
        “--json means” control on the other three tabs: raw API JSON re-exposes every
        null and every echoed field the whole project exists to avoid; lean fields as JSON keeps
        the token savings but is a different fidelity promise than “the real API response, machine-readable.”

      
Watching both renderings side by side: raw is 40–60× heavier for save_issue with
        no information a human or agent asked for. Lean-as-JSON reads like the natural third tier.

    

    

      
2. Are nulls omitted, or rendered?

      
Toggle “omit null/empty fields” on the save_issue / get_issue tabs. Omitting is strictly
        cheaper; the risk is a caller not knowing whether a field is absent because it's empty or because lean
        mode dropped it.

      
Candidate resolution: omit by default in lean and verbose; --json
        (lean-fields mode) always renders every lean-tier key, using null explicitly,
        since JSON output is the tier a script parses and cannot afford ambiguity.

    

    

      
3. Stable/parseable, or human prose?

      
Toggle “verbose style” on the get_issue tab. key: value lines
        are grep-able and diff-friendly; prose reads better cold but nothing should script against it.

      
Candidate resolution: lean and verbose are explicitly human/agent-readable text, not a
        contract — --json is the only tier meant to be parsed.

    

    

      
4. Does output shape depend on TTY, or only on flags?

      
Not something a static comparison can render meaningfully — this is a behavioural choice, not a
        rendering choice.

      
Confirms charting's lean-toward-flags-only: an agent's non-interactive stdout must not
        silently change shape depending on how it happens to be invoked. TTY-sniffing stays out of scope.
